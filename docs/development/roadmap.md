# 全量实施与验收顺序

本路线覆盖两个1.18.2 Mod的全部范围。各阶段最终覆盖所属系统全部内容；实施批次可以按完整功能族或玩家路径划分，不把抽样功能作为整个系统的交付范围。技术检查可以先定位某个API问题，但抽样通过不能抵消剩余内容。

负责人2026-11-02批准整体架构、工程结构与本路线，2026-11-03认可B1出口。A、B0步骤1–5、B1历史结论保持；B0其余机制随首次实际需要的系统落地。完整批准范围不变，当前实现与验收覆盖见[开放工作清单](remaining-work.md)，实际分支和下一动作见[交接](handoff.md)。本路线不再追加会话级进度快照。

2026-11-12负责人批准改进阶段自洽性与效率：工作包顺序用于组织依赖，不能用已进入E推导C全部验收，也不能因C局部缺陷将整个项目回退。前序依赖若未接通，登记承接系统、具体接口/内容和闭合依据；影响承诺路径时不得宣布该路径完成，独立后续工作可推进。完整移植goal已清除，本次规则修订不重建。

B0 的切片使用真实来源内容并按正式结构编写，不是一次性原型；其台账状态如实记录，所属系统仍在本系统批次中完成。实体类型、方块实体、菜单、粒子提供器、状态效果和需要新代码类型的数据（附魔、群系、地物）随所属系统迁移，不进入 B1 的空壳登记。

D 中 material、storage、profession 完成后，D 的其余系统、E、F 可以在不同 worktree 并行；共享接口变更先合入 `main` 再继续。界面、实体表现和资源在所属系统实施时同步接入，H 是最终全量复核。F/G 的问题调查从 A 开始，不留到实现末尾才发现。

## B1 实施步骤

B1 的范围与出口见上表 B1 行。按顺序执行，每步在开发服务端与客户端实测，做法与结论写入[工程结构](engineering.md)，逐步记录在[项目月度记录](../systems/project/logs/2026-11.md)。

| 步骤 | 内容 | 状态 |

| 1 来源格式盘点 | 以 MCreator 元素定义（`elements/*.mod.json`）为来源，列出 B1 范围的元素类型与字段，确定工厂类型与内容表字段；划清“不依赖新代码类型”与“随所属系统迁移”（方块实体、菜单、GeckoLib 渲染、实体、粒子提供器、状态效果、附魔、群系、地物）的界线 | 2026-11-02 完成 |
| 2 内容表加载器与工厂 | `platform` 的 Codec 解码，未知工厂类型报出文件与条目，按单位登记到各自的 `DeferredRegister`；创造栏 | 方块、物品、植物、工具、普通盔甲与声音事件完成；动画方块、GeckoLib 盔甲、自定义模型盔甲与桶随所属系统 |
| 3 注册表导出与台账比对 | 开发服务端导出注册表，`check_ledger.py` 比对状态为“已注册”及以上的目标 ID | 2026-11-02 完成 |
| 4 资源转换工具 | 内容表、模型、方块状态、纹理、语言片段、声音片段，配方、掉落表、标签、进度的 1.21.1 格式；命名空间改写与同名资源处理；转换清单与覆盖检查 | 完成；实体、附魔、效果、群系、界面等的语言键随所属系统 |
| 5 结构 NBT 升级方式 | 实测定案 | 2026-11-02 完成：不预先升级，由游戏加载时升级 |
| 6 归属阅读与登记 | 按[系统设计](system-design.md)“归属判定”读每个元素的规则并改为“已读”，重跑转换，开发服务端与客户端核对，台账改为“已注册” | 2026-11-03 完成（负责人决定在 B1 内一次读完；3 个无规则物品的归属由负责人裁定） |
| 7 出口 | 逐条核对下列出口条件，结果写入[项目状态](../systems/project/README.md)与本表；可复用做法写入移植技能 references；负责人审阅后合入 `main` | 2026-11-03 完成：出口条件 1–6 已核对（[项目状态](../systems/project/README.md)“B1 出口核对”），负责人认可后合入 `main` |

步骤 7 的出口条件：

1. 台账：B1 范围内每条来源注册（方块、物品、方块物品、声音事件）为“已注册”或“批准调整”；需要新代码类型而随所属系统迁移的行逐条列在 `docs/reference/conversion/skipped.csv`，归属为“已读”；归属待裁定的行已裁定。
2. 一致性：开发服务端导出的方块、物品、声音事件与台账“已注册”行一一对应，`check_ledger.py` 的导出比对与转换清单覆盖 0 项问题。
3. 日志：开发服务端与 `runSmokeClient` 无缺失模型、纹理、翻译与声音定义；其余 ERROR 逐类说明来源。
4. 数据：配方、标签、战利品表、进度、结构加载无 ERROR；因引用随所属系统迁移的内容而跳过的条目列在 `data_skipped.csv`。
5. 口径：项目状态、各单位 README 与日志不把“已注册”写成玩法完成。
6. 技能：本批核实且可复用的方法（归属证据清单与阅读方式、无编辑器元素注册的归属、按单位登记声音）按技能“维护本技能”写入 references，项目事实不写入技能。

## 系统工作单与验证

按[移植技能](../../.claude/skills/minecraft-mod-porting/SKILL.md)选择可结束的功能批次，按[验证参考](../../.claude/skills/minecraft-mod-porting/references/verification.md)选最小充分检查。本项目只补充记录与出口含义：

1. 已有来源归属、公开操作与字段索引直接复用；新增或改变的边界才补读来源并更新系统README，不能每批重新全量调查。
2. **批次实现闭合**：本批列明的同族/玩家路径已实现，必要入口、消费者、保存/中断和表现已接通，所选风险验证通过；未接依赖仍明确开放，不能将部分路径说成整个系统完成。
3. **系统完整验收**：全部来源范围有处理结果，玩法、数值、生命周期与表现具有相应证据；本系统注册台账全部为“已验收”或“批准调整”。来源静态内容按静态内容验收，不必制造行为实现或逐条游戏测试。剩余跨系统依赖和待裁定行为未消除前不宣称完整验收。构建/ArchUnit、台账与文档、两端及风险路径的有效证据须覆盖当前实现，可复用未受影响的已有结果，不要求每个提交重跑。
4. **全量移植完成**：所有系统、H和I要求均闭合。历史“系统完成”声明只按当时明示范围理解，不用本次文档整理提升验收状态。
5. 每批只更新受影响记录；结果入月志一次，开放项在[统一清单](remaining-work.md)归并，文档职责见[文档维护](documentation.md)。提交/合并不替代上述出口判断。
