# 全量实施与验收顺序

本路线覆盖两个 1.18.2 Mod 的全部范围。各批次完成整个所属系统及其内容，不把抽样功能作为交付范围。技术检查可以先定位某个 API 问题，但抽样通过不能抵消剩余内容。

当前执行 A。负责人 2026-11-02 授权先建立开发环境，并要求按长期维护重新设计工程结构与移植流程；本路线即该设计中的流程部分，待负责人批准。工程结构见[工程结构与长期维护](engineering.md)。没有 goal 任务。

## 批次和出口

| 批次 | 完整工作包 | 前置 | 本批完成依据 |
| --- | --- | --- | --- |
| A 调查和方案 | 来源身份、全部注册/文件/状态/过程/编辑器图索引、关键调用链、19 系统正文、公共入口与依赖、工程结构、待裁定问题和开发文档 | 两个参考工程 | 提案可追踪到源码；负责人明确批准架构与范围后才能进入实现 |
| B0 架构验证切片 | 依赖升到当时最新补丁；代码骨架与客户端入口；ArchUnit 规则；台账 CSV 与 `check_ledger.py`；语言/声音片段合并；内容表加载；资源转换工具首个类型；一个玩家附件（Codec、死亡复制、同步）、一个 payload、一个方块实体与菜单、一个 GeckoLib 实体、一个代码注册转数据定义、一个 GameTest、一个 JUnit 规则测试 | A 批准 | 每项在开发服务端与客户端实际运行；两个命名空间的注册、资源与翻译实测；验证结果写回[工程结构](engineering.md)并移除对应“待验证” |

| D 材料和生产 | 先 materials、storage；再 alchemy、refining、talismans、life，可并行 | C 所需契约 | 全部输入/产物去向、职业进度、失败与装置生命周期完成 |

| F NPC、经济、任务 | npc → economy → quests → knowledge | C；D、E 的实际消费者 | 获取、消费、扣款、发奖和推进均接通；现场多人交互与保存恢复核对 |
| G 阵法和后期联动 | formations 全部分支；跨系统特殊功法和后期效果 | C～F | 每个分支都有实际消费者与反馈；源码断链按已批准取舍完成 |
| H 界面与表现终核 | 92 个菜单对应功能、额外 HUD/覆盖层/按键、文案、实体和物品渲染、动画/粒子/声音、管理面板 | 所有系统 | 操作与表现逐项确认；技术成功和视觉认可分别登记 |
| I 完整对照与发布 | 全量台账收口；1.18.2 与 1.21.1 对照；专用服务器/多人/性能场景；许可证与交付文档 | B～H | 所有条目有处理结果；所有批准范围内行为验收完成；发布仍按负责人授权 |

B0 的切片使用真实来源内容并按正式结构编写，不是一次性原型；其台账状态如实记录，所属系统仍在本系统批次中完成。实体类型、方块实体、菜单、粒子提供器、状态效果和需要新代码类型的数据（附魔、群系、地物）随所属系统迁移，不进入 B1 的空壳登记。

D 中 materials、storage 完成后，D 的其余系统、E、F 可以在不同 worktree 并行；共享接口变更先合入 `main` 再继续。界面、实体表现和资源在所属系统实施时同步接入，H 是最终全量复核。F/G 的问题调查从 A 开始，不留到实现末尾才发现。

## 系统工作单与验证

每个系统使用同一份正文和台账，按[移植技能](../../.claude/skills/minecraft-mod-porting/SKILL.md)的“系统工作单”推进，验证方式按[验证参考](../../.claude/skills/minecraft-mod-porting/references/verification.md)选择。本项目补充：

1. 开工前从[候选归属](../reference/legacy/inventory/ownership_proposal.csv)与[类归属](../reference/legacy/inventory/class_ownership.csv)整理本系统来源清单，核对系统 README 的待裁定事项；需要负责人决定的矛盾在实现前提请裁定。
2. 实施中按台账逐行推进状态，内容表、资源转换和行为代码随同一系统提交。
3. 系统完成条件：本系统台账行全部为“已验收”或“批准调整”；`gradlew check`（含 ArchUnit 与相关测试）、`check_ledger.py`、`check_docs.py` 通过；开发服务端与客户端启动无 ERROR；风险流程有 GameTest 或记录的实机检查；系统 README 状态、正文与月度日志更新；完成移植技能的回顾步骤。

本项目的登记位置为系统 README 状态、设计/架构/数值正文、台账 CSV 和月度记录。

## goal 启动条件

负责人明确批准提案并明确要求启动后，才创建 goal；届时目标必须引用批准版本、完整范围、裁定结果和完成条件。当前方案中的待裁定项不能自动视为批准，也不能在 goal 中静默缩减内容。无需为了准备提案创建或运行 goal。

本轮状态与检查结果见 [项目状态](../systems/project/README.md)。
