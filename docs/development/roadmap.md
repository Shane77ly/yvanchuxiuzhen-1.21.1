# 实施与验收顺序

## 批次原则

整体路线为“确定架构 → 核实旧规则 → 最小链验证 → 同系统全量迁入 → 跨系统闭环 → 整包验收”。下列顺序不表示允许删去后续范围；早期样例只是验证架构，完整范围仍包含两个旧工程全部内容去向。

每批开始前建立系统正文与行为台账；结束时更新实现状态、差异、测试证据和月度记录。代码、资源和数值不在没有系统归属的临时任务中长期堆积。每批保持可构建，不靠逐条生成空实现维持编译。

## 建议阶段

| 阶段 | 交付范围 | 验收出口与依赖 |
| --- | --- | --- |
| A：设计与来源 | 本轮架构、源文件指纹、注册/字段清单；下一步逐系统补行为边界与风险 | 四项目标已确认；模块/数据设计可评审；静态清单可重现。不是所有旧行为已核实 |
| B：技术最小原型 | 新 Gradle、单 Mod、两个命名空间样例、独立服务器、附件/组件、菜单、网络和定义加载 | 客户端及服务器可启动；样例物品和方块正常；保存/重登/死亡/跨维度/关闭菜单通过。验证后才锁定依赖版本 |
| C：成长与战斗骨架 | 旧版基础属性、修为待吸收、境界/寿元、一门功法、一项技能、一个普通生物；公共书籍入口 | “获得功法→学习→修炼→装备技能→战斗→保存恢复”走通；公式有旧证据。此时不宣称全功法或全部成长已完成 |
| D：库存与生产样例 | 材料、容器、职业进度、一条炼器及炼丹线路、装备属性消费；同批提供可获取入口 | 预览/投入/加工/领取/使用/失败/卸载/多人争用通过；职业与成长没有重复存档 |
| E：完整成长与能力 | 全功法/技能/神通/身法/飞行、特殊效果、雷劫、金丹/元婴/体质/轮回、本命法宝和饰品 | 各目录闭环；旧未闭合分支已核实或有裁定；后期范围不能因前期样例通过而推迟为“不支持” |
| F：完整生产与生活 | 全部炼器/炼丹/符箓、图纸丹方与容器、阵法、采集/种植/烹饪、缝纫/木工/装订/修理、蛊罐等相关线路 | 所有旧设施/菜单有对应职责；完整材料来源与产物消费者；复杂阵法先最小形态验证再全量 |
| G：经济、NPC 与任务 | 全货币、银行、商店、拍卖、NPC 对话/交易/关系、悬赏、任务、成就与管理配置 | 商品和奖励引用已迁内容；多人购买、重登与重启恢复；所有规则用旧来源核对。前置接口在 D 即验证 |
| H：世界与生物全量 | 全旧维度/群系/结构/城镇/副本、所有实体本体/形态/弹体、生成、采集、战利品、探索与传送 | 实际自然生成与跨界回程成立；以生存线路接通 E～G 内容。世界格式/结构原型在 B 提前验证 |
| I：整包收口 | 剩余静态内容、装饰/工具、GUI/HUD/按键、声画、语言、全部资源引用；完整性复核与性能验证 | 没有未处置的来源条目；真实旧新对照、多人、重载、生命周期和专用服务器证据齐全 |

阶段 E～H 可按依赖选取已闭合子批次交错推进，而不是将所有世界内容留到最后才发现格式不可用。具体开发工作默认单线完成当前闭环；架构中的模块化不自动授权并行修改公共存档或核心 API。

## 提前验证的高风险点

| 风险 | 最小验证安排 | 失败时的处理 |
| --- | --- | --- |
| 单 Mod 保留两个旧命名空间 | B 中各注册一个物品/方块，加载模型、标签、配方和一份结构 | 确认加载器与资源假设；必要时建立明确 ID 迁移，先修方案再全量迁入 |
| 附件/组件的复制与同步 | B 中登录、重生、维度往返、服务器重启 | 依据目标源码定位生命周期，修数据所有权而非叠加重复同步 |
| 老模型/动画与实体命中 | B/C 中一个有代表性的动画实体与弹体 | 明确模型库或原生适配方案后再复制全部资源 |
| 旧伤害与属性的互相依赖 | C 中手算和旧运行算例、状态/护盾与死亡触发 | 固定运算阶段与例外策略，不通过统一默认倍率掩盖不一致 |
| 多模式生产及跨存档资产 | D 中加工中断、输出满、争用、重载与重启 | 缩小事务范围，增加必要恢复记录；再接银行和拍卖 |
| 大阵扫描与跨维度 | F 前先验证最小阵位、供能、绑定和卸载 | 区分拓扑检测与权威效果；测量后决定索引和调度 |
| 旧维度与结构格式变化 | B 中代表性维度/结构的独立验证 | 将数据格式与投放规则分别迁移，不批量改字段后宣称完成 |

## 每条功能的完成状态

使用分开的状态字段，不用一个“完成”掩盖证据差异：

- `source_status`：仅注册 / 静态链已核实 / 旧版实机已核实 / 矛盾待裁定。
- `implementation_status`：未实现 / 部分 / 行为接通 / 已替代且有映射。
- `validation_status`：未运行 / 构建通过 / 自动化通过 / 新版实机通过 / 新旧对照通过。
- `decision_status`：无需裁定 / 待裁定 / 已采用例外，附决定及影响。

最终验收按行为与内容去向共同判断。内部状态合并可减少目标注册数，但必须证明全部旧用途仍被承担。不能用“目标物品数接近旧版”代替完整移植。

## 测试层级

公式/解码/边界用小型确定性测试；库存、附件、网络和生命周期用服务端集成或 GameTest；专用服务器启动检查端隔离；真实客户端检查 GUI、操作、模型、动画、声音与反馈。旧版实机是判断源码矛盾及可见行为的必要补充。

旧版测试基线应记录版本、种子、角色状态、输入、时间/随机条件和结果。同类规则建立少量可信算例，再扩展表驱动内容覆盖；不为每个纯注册类写相同测试。

性能测试使用固定场景、固定机器和相同输入比较：多人在线、密集实体、连续施法、大阵、批量加工、跨维度与长时间运行。保留 tick、内存和网络证据；不以主观流畅代替测量。
