# 数据与运行时

本方案以“一个所有者、一套写入入口、按需派生显示”为原则。模块名称与总体依赖见[整体架构](architecture.md)。下述编码方式、接口和生命周期均为待实现方案，目标 API 已核对的范围见[API 证据](../reference/target-api.md)。

## 数据归属

| 数据 | 唯一所有者 | 存储建议 | 修改、消费与同步 |
| --- | --- | --- | --- |
| 功法/技能/药材/图纸/商品等静态定义 | 对应玩法系统 | 数据包 JSON、Codec 与加载后的只读目录 | 启动/重载校验后发布；系统服务查询；客户端只收所需展示定义 |
| 境界、修为、待吸收池、寿元、体质、金丹/元婴进度 | cultivation | 独立玩家 Attachment | 成长命令修改；属性和任务读视图；个人成长快照 |
| 功法学习、等级、经验、主修/装备状态 | gongfa | 独立玩家 Attachment | 学习、修炼和装备命令修改；书籍与 UI 只读 |
| 已学/装备能力与需持久保留的能力进度 | abilities | 独立 Attachment | 装备/学习命令；施法读取；冷却持久性逐技能核对 |
| 炼丹、炼器、符箓及生活职业经验 | 各职业模块 | 各自 Attachment 或模块内部同一档案 | 职业所有者结算，公共面板组合查询，不建立第二份“副职总表” |
| 装备、丹药、书籍、图纸、法宝实例 | 产物所属系统 | 类型化 ItemStack Data Component | 用新值替换组件，定义 ID 与实例覆盖分开；容器携带物品即携带其数据 |
| 饰品槽、本命槽、随身专属栏 | equipment/storage 对应所有者 | 玩家 Attachment 内物品集合 | 服务端库存接口修改；菜单使用真实容器；死亡策略逐槽定义 |
| 炉内物品、炉次、阵法装置与普通容器 | 对应方块系统 | BlockEntity 的库存与带版本状态 | 服务端变更后标记保存；打开菜单者接收槽位和专用视图 |
| 生物等级、主人、成长、形态 | creatures/npc | 实体 NBT/附件；必要展示字段用实体同步数据 | 实体生命周期内修改；跟踪者接收表现数据，完整档案不广播 |
| 银行、拍卖、全服任务/城镇实例 | economy/quests/world 各自所有者 | 明确范围的 SavedData | 世界主线程服务修改并标脏；账户不因玩家离线丢失；全服数据固定归主世界存储 |
| 维度局部场景、装置索引 | world 或对应系统 | 该维度 SavedData；索引可重建 | 存 UUID、维度键与坐标；不持久化 Java 实体引用 |
| 属性汇总、UI 数据 | attributes/各系统展示层 | 派生缓存，不作为第二份存档真值 | 来源变更时失效并重算；专用快照发给本人或查看者 |
| 施法会话、目标缓存、命中集合、短期特效 | 对应玩法运行态 | 每个服务器/世界的运行态容器 | 按旧规则推进；停止、离线、换维度、卸载时清理 |

持久化包含 `schema_version`；网络协议版本、数据包定义版本和存档版本分别管理。定义是“物品/功法是什么”，实例是“这一本、这件装备的成长和覆盖值”，会话是“当前正在执行什么”；三者不放在同一 CompoundTag 中任意读取。

## 加载与保存

1. 注册阶段登记静态类型、附件、组件、菜单、网络消息。数据包重载不能动态新增 Item/Block 注册项。
2. 开服加载世界数据和玩家档案，按版本逐步解码/迁移，保留无法识别的原始数据或明确拒绝不支持版本；不静默清空档案。
3. 校验定义引用，再重算派生属性。未找到定义时禁用对应操作并报告定位信息，不用默认新物品覆盖原实例。
4. 所有者提交变化，更新 revision/脏标记，派生消费者按变化重算，并通知相关客户端。
5. 玩家、实体、方块和世界分别通过所属保存通道写入；不得假定只调用网络同步就完成持久化。

附件 `copyOnDeath` 只用于确认需要复制的档案。普通死亡、寿尽、轮回、末地返回是不同流程；新旧实体复制与玩法惩罚不能由两个监听器各执行一次。基础档案、物品栏、本命槽、任务、银行和技能冷却各自写出继承/扣除表后再实现，当前不统一设为全部保留。

## 服务端操作协议

客户端发送“做什么”，不发送可信的“我已经得到了什么”。例如 `StartRefining(menuId, expectedRevision, recipeId, mode)` 只描述请求；服务端从当前菜单、实际容器、距离、维度、职业状态和定义重新获取输入。

对于库存、余额、领奖等操作，采用同一服务器主线程上的“校验 → 计算计划 → 复核相关版本/容量 → 提交变化 → 更新状态与反馈”。预览不消耗库存、不推进随机数、不写入正式经验。输出不够时是否停机、弹出或失败必须按旧规则确定，不能统一默认丢弃。

连续按钮请求用菜单 ID、操作状态/序号、revision 与当前库存复核约束；协议限长并校验 ID、范围、距离和权限。拍卖成交、跨账户转账、奖励领取等需要持久事务编号与状态恢复，提交、重登和重试均验证结果。不能把内存中的已处理集合称为跨重启“恰好一次”。

Minecraft 不提供覆盖玩家文件、区块和多个 SavedData 的通用数据库事务。跨保存对象的资产转移应缩小事务范围，或使用可恢复的记录与交付状态；进程中止/重启恢复是单独验收项，不把“同一 tick 执行”当作磁盘原子性。

## 同步分层

| 通道 | 内容与接收者 | 时机 |
| --- | --- | --- |
| 玩家个人快照 | 成长、功法、职业等所需展示字段，仅本人 | 登录/重生/换维度初始化，状态变化后合并发送 |
| 实体跟踪同步 | 形态、动作阶段、必要等级等，当前跟踪者 | 开始跟踪与关键状态改变；不依赖旧包补齐初始状态 |
| 菜单同步 | 槽位、加工阶段、进度、预览、错误反馈，仅查看者 | 打开全量，后续按变化；大值/浮点走明确编码，不随意塞入短整数槽 |
| 定义展示同步 | 客户端真正需要的定义摘要、版本和内容 | 登录与成功重载后；设分片和大小上限 |
| 视觉消息 | 技能标识、施法实例、时间、位置与参数 | 服务端行为确定后发给相关玩家；不决定扣费、伤害或奖励 |

客户端快照携带会话/版本与 revision。重登、切服、维度切换和菜单关闭清除不再有效的缓存；过期快照不得回滚当前视图。表现缺失不能阻止服务端结算，客户端本地预测不得成为权威命中。

## 定义重载

将有跨系统引用的自定义定义构建成一个候选快照，完成 schema、ID 唯一性、引用、范围、单位与环依赖检查后再发布。启动没有有效快照时失败并定位资源；运行中失败则保留上一份完整自定义快照并明确报告。本地 NeoForge 的 reload 事件仅提供接入点，不自动保证这一事务，需要实现并测试。

自定义快照依赖的原版 tags/recipes/dynamic registries 也会重载，不能宣称旧快照与新原版资源天然一致。应使用重载完成后的 registry lookup 校验；失败时暂停受影响的新操作，避免混合代际继续运行。

已经开始的炉次应保存开始时确认的必要输入、规则版本与结果计划，是否冻结随机结果按旧行为核对；不能只保存一个易被重载替换的对象引用。移除定义不删除已有物品，运行中技能、阵法、NPC 报价分别规定继续、重算或中止策略。重载后使属性缓存失效，重发需要的展示信息；不依赖玩家重新登录才能恢复。

## 运行态与性能

- 统一生命周期入口负责注册各系统的活动会话；每个系统管理自己的状态机。避免几十个 Tick 监听器重复扫描全部玩家、实体和物品。
- 只推进活动炉次/阵法/施法。范围查询绑定维度与区块，结构拓扑按方块变化或明确检查周期更新；缓存必须有失效条件。
- 旧版按 tick/秒推进的数值、触发频率和随机顺序属于玩法基线。预算优化不能偷偷跳过伤害 tick 或改变产量；分批调度应只用于允许延迟的非权威准备工作，必要行为延迟作为明确差异评审。
- 保存 UUID、维度键、坐标和失效状态，不跨世界持有全局 Player/Level/Entity 强引用。服务端停止时释放运行态；客户端退出时清理表现。
- 区块卸载默认不强制加载继续工作。炉次、阵法、拍卖、任务的离线/卸载时间语义分别核对，不能自动加入离线收益或全地图常驻 ticket。
- 可观察指标包括活跃会话数、每类查询次数、重载耗时、同步字节数、tick 耗时及积压。最终预算以代表性多人、阵法和生物场景实测，不在架构稿中编造已达标数值。

## 必测边界

最小集包括：档案/组件往返与版本迁移；普通死亡与非死亡复制；重登及跨维度；菜单关闭再开/移走物品/多人操作；重复请求与无空间；炉次保存中断；银行/拍卖重复交付；成功和失败重载；专用服务器无客户端类加载；视觉消息缺失时权威结果一致。

实现状态：这些约束尚未由代码、单元测试或 GameTest 实现；旧版死亡与离线细节仍需逐链确认。
