# 范围与保真原则

## 已确认的目标

2026-11-01，负责人要求从全新项目开始，完整移植参考目录中的两个旧 Mod，先设计整体架构；随后确认目标为 Minecraft 1.21.1 + NeoForge + Java 21，合并发布一个 Mod，内部按系统分模块。

来源均为 0.5.2 / Minecraft 1.18.2 / Forge 40.1.0 / Java 17 的 MCreator 工程。旧元数据互相声明必需依赖。旧工程是共同构成玩法的两部分；新项目的边界按玩法职责与数据归属重新组织。证据见[来源入口](../reference/legacy/README.md)。

本轮完成设计稿和静态清单，不开始大批复制注册代码、生成占位实现或移植玩法。后文为建议方案，除上述四项外不表述为负责人已采用决定。

## 完整的判定

完整范围包含两个 Mod 的物品、方块、实体及形态、技能/功法、成长、生产、装备、世界、交易、任务、生活设施、操作界面、资源与管理工具。蛊虫、容器、银行、拍卖、职业、副本等不能继承旧移植工程的“暂缓”作为本项目的永久排除。

每个旧条目都应有可追踪去向：等价实现、同功能合并、内部状态替代，或者有证据并经过裁定的例外。仅有注册且未找到行为的内容保留核对任务，不能自动标记无效、移植完成或自行补造玩法。

每条玩家线路按“获得入口 → 条件 → 操作 → 成本 → 结果 → 后续消费者 → 保存与恢复”核对；包括失败、取消、死亡、跨维度、断线和多人争用。界面职责、反馈、声画表现及自然投放属于对齐范围。内部类名和文件结构无需复制。

## 玩法规则与技术改造的边界

| 情形 | 建议处理 | 必须留下的证据 |
| --- | --- | --- |
| 来源明确且调用有效的规则 | 保留数值、顺序、单位、取整、概率和触发条件 | 旧入口、调用链、算例或运行记录 |
| API 已移除或跨端混乱 | 重写技术实现，保持可见行为 | 旧行为、新数据流与对照场景 |
| 客户端信任、重复发奖、数据破坏 | 按服务端权威与完整性约束修复，并列为行为差异 | 可复现触发、修复结果和回归验证 |
| 两段源码公式冲突、预览与产物不同 | 分别记录实际消费者，先列待裁定 | 两条路径、玩家影响，禁止择优猜测 |
| 有注册、无入口或未完成玩法 | 保留条目并查明状态；不编造缺失部分 | 检索范围、未找到什么、待验证场景 |
| 只在当前 1.21.1 旧移植工程存在的新机制 | 不进入旧版对齐基线 | 如以后采用，单独登记新设计与来源 |

“完整移植”不等于照搬两套 PlayerVariables、字符串配置表和 Procedure 结构；也不意味着借迁移重新平衡已有玩法。

## 技术路线建议

采用直接面向 1.21.1 的分系统重写，不维护临时 1.19/1.20 版本。理由是旧工程的关键耦合集中在状态、注册与过程调用，而不是需要通过中间版本才能恢复的源码工具链。先验证最小运行链，再按同一架构迁入内容；资源可以批处理，行为必须逐链核对。

新旧工程在独立目录和 Git 仓库中维护。现有新版本代码只有在确认职责、依赖、旧版行为和验证范围后，才能择项复用。禁止整包继承已有功法、心湖、区域灵气、异火、界面和数值设计。

## 本轮不代替裁定的事项

- 旧版自相矛盾的功法副本、炼器预览/产物公式、阵法断路和后期未闭合行为。
- 旧地图的直接升级、两个旧命名空间存档的离线导入，以及已有 1.21.1 重做存档的迁入。建议首个版本以新世界验收；内容 ID 保留不等于旧存档兼容，这项兼容范围需单独决定。
- UI 是否逐像素复刻：建议保留操作能力、槽位、反馈和信息，布局另做客户端验收，不默认套用已有重做界面。
- 仅有后台编辑入口的旧内容应如何发布：先登记管理职责与权限，再确认自然生存获取链。

上述问题分别在实施到相关系统前解决，不阻碍建立公共架构； unresolved 条目不得从完整性分母中消失。

实现状态：尚未移植任何游戏功能；未运行旧版或新版游戏。
