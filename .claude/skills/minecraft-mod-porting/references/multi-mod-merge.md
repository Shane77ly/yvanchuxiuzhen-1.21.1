# 多个来源 Mod 合并

已核对范围：两个互为必需依赖的 MCreator 生成 1.18.2 Forge Mod 合并为一个 NeoForge 1.21.1 Mod 的调查阶段。保留多个命名空间的方案尚未经过构建与运行验证。

## 命名空间

- 保留各来源命名空间，可减少模型、配方、标签、结构 NBT、命令字符串、物品表和世界引用的无意变化；但不等于来源 Mod 的二进制 API 或来源版本世界可直接运行。
- 目标加载器能否由一个 Mod 注册多个命名空间，以及资源加载、翻译、结构解析与打包是否正常，先查目标源码，再在基础阶段实测。
- 映射键为“注册表类型 + 原命名空间 + 原路径”。不同命名空间下的同名路径不构成冲突，也不能直接归并；只有压平命名空间时才需要改名。
- 显式改名或合并须在映射台账登记规则与资源引用变换，不做全文替换，也不按显示名匹配。
- Java 包名和代码模块边界可以重新规划，不受来源命名空间限制。

## 依赖与跨 Mod 调用

- 删除来源之间的相互依赖声明。凡以“某个 modid 是否加载”决定行为的代码，逐处改为新项目内部的能力判断。
- 来源之间直接读写对方状态（例如一个 Mod 读取另一个 Mod 玩家数据中的等级，再写入自己的方块）要在调用链中逐处识别，合并后改为明确的系统接口，并保留“快照”与“实时读取”的语义差异。
- 多个来源可能声明同名状态字段。同名不证明同义：按类型、读写者和消费者确认后，再决定是否合并为一个真值。
- 第三方依赖按实际使用判断。构建脚本或编辑器工程的声明、元数据的 optional 标记与代码实际引用可能不一致。
