# 多个来源 Mod 合并

已核对范围：两个互为必需依赖的 MCreator 生成 1.18.2 Forge Mod 合并为一个 NeoForge 1.21.1 Mod 的调查阶段，以及保留与统一命名空间的取舍（静态统计与目标源码核对；统一后的运行验证尚未完成）。

## 命名空间

- 两种做法：保留各来源命名空间，或统一为目标 Mod ID。在首次发布前决定；发布后再改会使目标版本自身的存档丢失内容。
- 保留的好处是来源 ID 与资源中的引用（模型、配方、标签、结构 NBT、命令字符串）不变，便于承接来源版本存档；但不等于来源 Mod 的二进制 API 或来源版本世界可直接运行。
- 保留的代价持续存在：目标按职责划分模块时，一个模块常同时含多个来源的内容，注册器、内容表、语言与声音资源都要再按命名空间分一层，新增内容也没有应归的命名空间；加载器若以注册名的命名空间作为物品的创建者 Mod，物品浏览类 Mod 会显示一个不在 Mod 列表中的来源名。
- 统一的代价是一次性的：先统计同一注册表下的同名路径，以及资源目录中相对路径相同的文件（区分字节相同与不同）；同名者读来源确认是否同一内容，逐个改名并在映射台账登记；资源中的 ID 引用（JSON、语言键、结构 NBT 方块调色板）由转换工具改写。需要承接来源版本存档时，用目标加载器的注册表别名把旧 ID 解析到新 ID，并实测区块、物品与玩家数据读取。
- 映射键为“注册表类型 + 原命名空间 + 原路径”。保留命名空间时，不同命名空间下的同名路径不构成冲突；统一时它们成为冲突，同名不证明同一内容，读来源后再决定改名或合并。
- 显式改名或合并须在映射台账登记规则与资源引用变换，不做全文替换，也不按显示名匹配。
- Java 包名和代码模块边界可以重新规划，不受来源命名空间限制。

## 依赖与跨 Mod 调用

- 删除来源之间的相互依赖声明。凡以“某个 modid 是否加载”决定行为的代码，逐处改为新项目内部的能力判断。
- 来源之间直接读写对方状态（例如一个 Mod 读取另一个 Mod 玩家数据中的等级，再写入自己的方块）要在调用链中逐处识别，合并后改为明确的系统接口，并保留“快照”与“实时读取”的语义差异。
- 多个来源可能声明同名状态字段。同名不证明同义：按类型、读写者和消费者确认后，再决定是否合并为一个真值。
- 第三方依赖按实际使用判断。构建脚本或编辑器工程的声明、元数据的 optional 标记与代码实际引用可能不一致。
