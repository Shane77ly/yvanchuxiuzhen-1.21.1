# Minecraft Mod 移植

本技能规定移植作业的通用方法。项目的具体事实、决定和规范由项目指令文件（AGENTS.md、CLAUDE.md 等）及项目文档提供；二者冲突时以项目指令为准，并向负责人说明冲突。

## 1. 读取项目档案

开始前从项目指令文件读取下列信息。缺项不猜测：调查阶段标为“待确认”后继续，实施阶段先询问负责人。

| 项 | 内容 |
| --- | --- |
| 来源 | 每个来源 Mod 的名称、modid、版本、加载器、位置及锁定标识（提交、哈希或发布版本） |
| 目标 | Minecraft 版本、加载器及版本、Java、发布形态 |
| 范围 | 全量，或负责人批准的子集 |
| 目标源码 | 目标加载器精确版本的本地源码位置 |
| 非依据 | 已有移植、分支、其他版本等只能作参考的工程 |
| 当前关口 | 所处阶段与已批准事项 |
| 记录位置 | 内容映射、行为对齐、验收证据、规则正文和日志的位置 |

## 2. 核心规则

1. 来源的实际行为是规格。依据为锁定版本的源码、资源及编辑器工程；名称、注释和文档描述不能替代调用链。
2. 已有移植、分支、重做版和其他游戏版本只作检索与工程参考，不继承其新增玩法、数值、删减范围、UI 取舍或完成状态。
3. 范围由项目决定。分批实现不等于缩减交付范围，不得自行改成最小功能项目。每项来源内容都有去向：保持身份并实现、由等价内部表示承担、经批准的行为调整、待核实。没有找到调用者不能删除；只注册占位内容不能标记完成。
4. “建议”“待裁定”“待核”不是已采用决定；已采用但未实现的规则明确标注。
5. 不得用空实现、静态注册、文档描述或编译通过宣称移植完成。静态注册、事件挂载、正确运行、行为对齐分别记录。
6. 来源中的矛盾、疑似错误或消费断链，不自行重平衡、不补造玩法、不按“更合理”修正；先记录入口、实际效果、来源位置和影响，再提出取舍，裁定前保持来源行为。
7. 编写或评审目标加载器机制前，先阅读目标精确版本的源码。无法从该版本源码确认的行为标为“待验证”，不套用其他版本或其他加载器的经验。
8. 逐系统核对注册、事件、同步、持久化、菜单与渲染的生命周期。
9. 证据分级登记：静态源码核对、自动化验证、来源版本实机、目标版本实机、两版本对照；未执行的写“未执行”。模型、粒子、渲染的技术检查不等于视觉认可；构建通过不等于运行或行为对齐。

| 情况 | 处理 |
| --- | --- |
| 已核实有效的玩法 | 保留数值、顺序、单位、概率、实例归属和触发条件 |
| API 或资源格式变化 | 按目标版本重写实现，保留玩家可见结果 |
| 来源冲突、疑似错误、消费断链 | 按规则 6 记录并提请裁定 |
| 无明确运行入口的注册或类 | 继续检查事件、命令、资源、结构与动态调用，状态写“待核实” |

## 3. 阶段关口

调查与方案 → 负责人批准架构与范围 → 分批实施 → 全量对照与发布。未经明确批准不开始游戏实现，也不创建自动长任务。批准内容中的待裁定项不视为已批准。

## 4. 系统工作单

每个系统按以下顺序完成：

1. 固定来源：注册 ID、过程与事件入口、资源、动态配置和状态载体。
2. 追踪玩家路径：获得 → 条件 → 操作 → 成本 → 结果 → 后续用途 → 保存与恢复。菜单反馈、声音、动画、失败和中断都属于功能。冲突按规则 6 处理。
3. 按已批准的数据归属实现，迁移同族全部内容及特殊分支。
4. 按风险选择验证，登记各级证据。
5. 更新项目正文、实现状态与日志；剩余项保留具体 ID。
6. 回顾本系统：新核实且可复用的转换、来源结构知识和检查项按第 6 节写入 references；发现本技能内容有误时修正或删除。项目专有决定写入项目文档。

## 6. 维护本技能

- 只写通用方法和已核实知识；不写项目路径、项目内容 ID、负责人决定或大段来源代码。
- 版本或库相关的事实注明核对的精确版本与依据（源码文件或实测场景）；推断内容写“待验证”。
- 每个参考文件开头写明已核对范围。
- 通用移植规则只在本技能保存一份正文；项目文档链接引用，不复制。
