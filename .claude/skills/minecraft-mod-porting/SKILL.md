# Minecraft Mod 移植

本技能规定移植作业的通用方法。项目的具体事实、决定和规范由项目指令文件（AGENTS.md、CLAUDE.md 等）及项目文档提供；二者冲突时以项目指令为准，并向负责人说明冲突。

## 1. 读取项目档案

首次接手从项目指令和交接读取下列信息；续批只读当前任务、关联正文与基线后的差异。缺项先查已有证据，只有影响当前实现且无法自行核实的决策才询问负责人，不暂停独立工作。

| 项 | 内容 |
| --- | --- |
| 来源 | 每个来源 Mod 的名称、modid、版本、加载器、位置及锁定标识（提交、哈希或发布版本） |
| 目标 | Minecraft 版本、加载器及版本、Java、发布形态 |
| 范围 | 全量，或负责人批准的子集 |
| 目标源码 | 目标加载器精确版本的本地源码位置 |
| 非依据 | 已有移植、分支、其他版本等只能作参考的工程 |
| 当前进度 | 实际代码基线、实现覆盖、开放缺口与已批准事项；不以单个阶段字母概括全部状态 |
| 记录位置 | 内容映射、行为对齐、验收证据、规则正文和日志的位置 |

## 2. 核心规则

1. 来源的实际行为是规格。依据为锁定版本的源码、资源及编辑器工程；名称、注释和文档描述不能替代调用链。
2. 已有移植、分支、重做版和其他游戏版本只作检索与工程参考，不继承其新增玩法、数值、删减范围、UI 取舍或完成状态。
3. 范围由项目决定。分批实现不等于缩减交付范围，不得自行改成最小功能项目。每项来源内容都有去向：保持身份并实现、由等价内部表示承担、经批准的行为调整、待核实。没有找到调用者不能删除；只注册占位内容不能标记完成。
4. “建议”“待裁定”“待核”不是已采用决定；已采用但未实现的规则明确标注。
5. 不得用空实现、静态注册、文档描述或编译通过宣称移植完成。静态注册、事件挂载、正确运行、行为对齐分别记录。
6. 来源中的矛盾、疑似错误或消费断链，不自行重平衡、不补造玩法、不按“更合理”修正；先记录入口、实际效果、来源位置和影响，再提出取舍，裁定前保持来源行为。
7. 首次使用或改变目标加载器机制时，以精确版本源码核实。已有同版本、同机制的来源位置与结论可直接复用；只在版本、相关代码或证据发生变化时重核。无法确认的行为标为“待验证”，不套用其他版本或加载器的经验。
8. 逐系统核对注册、事件、同步、持久化、菜单与渲染的生命周期。
9. 证据分级登记：静态源码核对、自动化验证、来源版本实机、目标版本实机、两版本对照；未执行的写“未执行”。模型、粒子、渲染的技术检查不等于视觉认可；构建通过不等于运行或行为对齐。

| 情况 | 处理 |
| --- | --- |
| 已核实有效的玩法 | 保留数值、顺序、单位、概率、实例归属和触发条件 |
| API 或资源格式变化 | 按目标版本重写实现，保留玩家可见结果 |
| 来源冲突、疑似错误、消费断链 | 按规则 6 记录并提请裁定 |
| 无明确运行入口的注册或类 | 继续检查事件、命令、资源、结构与动态调用，状态写“待核实” |

## 3. 阶段关口

调查与方案 → 负责人批准架构与范围 → 分批实施 → 全量对照与发布。未经明确批准不开始游戏实现，也不创建自动长任务。批准内容中的待裁定项不视为已批准。

实现覆盖与验收覆盖分别记录。进入后续工作包不等于前面所有内容已验收；发现前序遗漏也不自动使整个项目退回前序阶段。只有证据显示共享基础或前置契约失效时，才重开受影响关口，并列出失效结论、受影响消费者与修复范围。局部缺陷只重开对应功能。

每个批次先确定可结束的功能边界：完整同族或玩家路径、所属系统、必要消费者、本批所需验证。跨系统余项登记具体接口/内容、承接系统、依赖条件和完成依据；不能只写“随后续系统”。若余项阻止本批承诺的路径可用，就不能宣布本批闭合；不相关的后续工作可以继续。已有合并和提交不作为完成证据。

项目只维护一份开放工作清单作为调度入口，链接已有规则和证据，不复制全部注册台账。类型至少区分未实现、确认缺陷、待核实/待验证、外部依赖、待裁定。同一问题只保留一个当前结论；已解决项移入历史记录，不在当前状态中继续叠加旧结论。

## 4. 系统工作单

首次实施建立功能清单；续批复用已有清单与证据，只处理选中的缺口：

1. 从实际分支/提交、当前清单和已读来源定位本批边界。注册 ID、入口、资源、动态配置和状态载体沿用既有索引，不重新全量调查。
2. 补齐本批玩家路径：获得 → 条件 → 操作 → 成本 → 结果 → 消费者 → 保存/中断恢复；同时处理本路径菜单反馈和必要表现。对同模板族核对差异后批量迁移，保留特殊分支。
3. 按数据归属实现，外部消费者通过已核实公开接口接入；本批无法接入的具体依赖写回开放清单，不临时无限扩大批次。
4. 实现前选定能发现本批实际风险的最小充分验证。修改完成后集中编译/检查；验证失败先区分产品、夹具与环境，按[验证参考](references/verification.md)处理，不将修检查代码计作玩法完成。
5. 在同一提交更新受影响台账、唯一规则正文和系统当前摘要；结果与证据只记一次，交接仅链接当前任务。报告本批闭合的功能、仍开放的具体项和验证边界，不以提交数或断言数表示完成度。
6. 仅在产生新知识或发现旧规则有误时维护技能参考；不为每个批次重复写技能回顾。项目决定留在项目文档。

## 6. 维护本技能

- 只写通用方法和已核实知识；不写项目路径、项目内容 ID、负责人决定或大段来源代码。
- 版本或库相关的事实注明核对的精确版本与依据（源码文件或实测场景）；推断内容写“待验证”。
- 每个参考文件开头写明已核对范围。
- 通用移植规则只在本技能保存一份正文；项目文档链接引用，不复制。
